# PACE-PC 报告审计

## 当前定位

`PACE-PC_idea-report.pdf` 是一份由对话生成的候选设计，不是文献综述、实验计划或已验证方法。它最有价值的部分是把讨论压缩成了“问题 - gap - 方法 - baseline - 数据集”；最大风险是把存在的论文、合理的类比和未经验证的新主张写在同一语气里，让读者误以为整套方案已经成立。

## 报告中尚未成立的主张

1. **“点云复合退化存在可学习的偏序”**：是研究假设，不是既有事实。需要定义哪些操作可交换、近似可交换或不可交换，并证明该关系对恢复有实际影响。
2. **Add/Move/Delete 足以覆盖目标退化**：着色、非刚体形变、视角遮挡、密度变化和传感器噪声未必能被三个原子无歧义表示。
3. **可获得退化程序轨迹监督**：如果在线合成可以得到轨迹，模型可能只学习合成器规则；真实数据没有对应程序标签。
4. **从二阶组合泛化到反序和三阶组合**：这是核心实验命题，不应在方法描述中预设成功。
5. **局部 UOT 是合理辅助约束**：需要确认 UOT 对当前编辑语义的对应关系，不能只因相邻论文使用过就认为适用。
6. **4090 可完成全部训练**：报告没有给出经过测量的 batch、点数、epoch、显存和墙钟时间。
7. **CPCCD-Program、seen/unseen 划分**：是拟建协议，不是现成 benchmark；必须检查组合泄漏和训练/测试难度是否等价。
8. **“首次”“真正缺少”**：需要主张级系统查重，不能由 Codex 对话直接得出。

## 最严重的技术风险

### 1. 顺序的因果语义可能不稳定

点云退化操作在离散采样、随机参数和归一化之后，是否可交换可能取决于实现细节，而不是物理规律。若标签由合成脚本定义，模型可能学到脚本指纹。

### 2. 逆程序不一定唯一

同一个退化点云可能由多个操作序列产生；恢复到同一 GT 也可能存在多条等价路径。强制唯一顺序会制造错误监督，偏序也未必完全解决可辨识性。

### 3. benchmark 贡献可能压过模型贡献

如果核心新意是新的组合划分，需要把协议本身做扎实：退化强度、组合频率、分布外定义、泄漏检查和真实域对应。否则模型和 benchmark 都显得不完整。

### 4. 实验规模可能远超小论文预期

原子种类、顺序、强度、组合阶数、数据集和 baseline 会形成组合爆炸。必须先限定一个核心故事，否则单卡周期失控。

## 五个立项闸门

只有全部通过，PACE-PC 才值得进入 baseline：

1. **查重闸门**：全文核验最近 3 年组合点云恢复、程序化退化、顺序恢复与可组合编辑工作。
2. **定义闸门**：给出退化原子、交换关系和 ground-truth 生成规则，并证明不是脚本任意性。
3. **最小反例闸门**：在两个数据集上证明顺序确实改变恢复难度，且固定顺序/无序路由无法解释。
4. **算力闸门**：官方 baseline 在 4090 上实测显存和时间，得到完整预算。
5. **导师闸门**：博士对“问题是否成立”作技术评审，而不是只评方法听起来是否新。

## 当前建议

保留 PACE-PC 作为高风险候选，不立即把它定为 CCF-C 主线。先用 3 到 5 天做定义与最小反例验证；如果顺序效应不稳定，就及时退出，转向更清晰的公开数据问题。不要因为报告写得完整，就误把“叙事完整度”当成“科学可行性”。
